この`triage`ブランチは調査結果と実装判断を保存する記録用ブランチです。PRやmainへのマージを目的にしません。

## 次の作業を選ぶ手順

1. [タスク台帳](tasks.md)の固定ID・状態・依存を確認し、記録の日付・main SHAを確認し、`jj git fetch --all-remotes`とghでIssue、open PR、originブックマークを再取得する。
2. バグ対応を優先し、既存PR・準備済みブランチとの重複と本体API依存を確認する。後段スタックは前段マージまでPRを出さない。
3. 構造改善は[タスク台帳](tasks.md)の着手可能一覧・状態・依存と、対応する検証記録を参照して選ぶ。PUSHEDの作業は再実装せず、公開指示を待つ。READMEに進捗を重複記載しない。
4. 実装は最新mainから別ブランチを作る。triageを親にしない。既存ブランチを無断で書き換えない。
5. 赤→緑、関係するテスト・ビルド、必要な実サーバー確認の証拠を残す。検証済み／ドキュメント根拠／推測を区別し、確認できていないものは未検証と書く。
6. Issue全体を満たす場合だけFixes/Closesを使う。部分移行はRefsと残件を明記する。再現しない場合は確認範囲付きのコメント・再確認依頼を検討する。
7. 実装・マージ・検証・投稿で状態が変わったら、tasks.mdの該当行と作業順を同時に更新する。日付付き文書へだけ追記して台帳を古くしない。公開コメントはURLを記録し、未投稿との矛盾を防ぐ。履歴を現在の結論に見せない。

基準main・現在の実装順序・マージ待ちはタスク台帳にのみ記載する。PR・準備済みブランチの現在の状態はタスク台帳を参照し、ここには件数を重複記載しない。

```text
jj file show -r triage triage/README.md
jj file show -r triage triage/2026-11-12-angular-modernization.md
jj file show -r triage triage/2026-11-10-bug-triage.md
```

jj/ghはmise管理下の実体を直接呼ぶ。ローカルtmpの証拠はGit管理外なので、将来存在する保証はない。公開コメント、固定SHA、PRと併せて参照し、必要なら再実行する。
